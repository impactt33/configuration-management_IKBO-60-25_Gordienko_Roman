# Граф зависимостей Python — вариант 7

Приложение получает прямые зависимости выбранной версии пакета и строит
граф транзитивных зависимостей алгоритмом BFS без рекурсии. Можно использовать
реальный индекс Simple API или локальный JSON-репозиторий.

## Запуск

Нужен Python 3.12 или новее. Зависимости перечислены в `requirements.txt`.
Команды ниже выполняются из корня проекта `ConfigManagement`:

```bash
.venv/bin/python -m pip install -r hw2/requirements.txt
bash hw2/run.sh --help
```

`run.sh` использует Python из `.venv` в корне проекта, если он существует.
Иначе используется `python3`. Переменная `PYTHON` позволяет выбрать другой
интерпретатор. Запускать скрипт можно и из `hw2`: `bash run.sh ...`.
Относительный путь в `--repo` считается от текущего рабочего каталога.

Пример сетевого режима:

```bash
bash hw2/run.sh --name httpx --version 0.28.1 --max-depth 2
```

| Опция | Назначение | По умолчанию |
| --- | --- | --- |
| `--name` | Имя корневого пакета; разрешены extras, например `httpx[http2]` | Обязательна |
| `--version` | Версия корневого пакета | Обязательна |
| `--repo` | Базовый URL Simple API или путь к JSON | `https://pypi.org/simple/` |
| `--test-mode` | Читать локальный файл без сетевых запросов | Выключен |
| `--max-depth` | Максимальное расстояние от корня по рёбрам, целое число от 0 | `3` |
| `--filter` | Исключать пакеты с указанной подстрокой в имени | Пустая строка |
| `--format` | Формат результата: `json`, `order`, `d2` | `json` |
| `--output` | Путь для сохранения результата; `.svg` включает рендеринг D2 | Только stdout |
| `--show` | Открыть созданный SVG в стандартном браузере | Выключен |

Корень находится на глубине 0. При `--max-depth 0` выводится только корень,
при `1` — корень и его прямые зависимости. Для узлов на границе выбирается
версия, но их собственные зависимости не запрашиваются. Ограничения сверху
на значение глубины нет.

Фильтр применяется до запросов версий и метаданных исключаемого пакета.
Сравнение не учитывает регистр; точки и подчёркивания в именах и подстроке
приводятся к дефисам. Зависимости исключённого пакета остаются в графе,
если до них можно добраться через другую разрешённую ветку. Если фильтру
соответствует сам корень, он остаётся в выводе без анализа зависимостей.

## Формат тестового репозитория

Файл UTF-8 содержит JSON-объект: имя пакета → версии → списки требований.
Имена пакетов состоят только из больших латинских букв, как требует задание.

```json
{
  "A": {"1.0": ["B>=1,<2", "C"]},
  "B": {"1.0": [], "1.5": [], "2.0": []},
  "C": {"1.0": []}
}
```

Для `A==1.0` будет выбрана версия `B==1.5`: это максимальная версия,
соответствующая `>=1,<2`. Версии сравниваются по правилам Python-пакетов,
а не как строки. Разрешены те же ограничения, extras и маркеры окружения,
что и при разборе сетевых метаданных. Прямые URL в требованиях тестового
репозитория запрещены. Ссылки на отсутствующие пакеты или неподходящие
версии приводят к ошибке, когда обход доходит до этой зависимости.

```bash
bash hw2/run.sh --test-mode --repo hw2/examples/branching.json \
  --name A --version 1.0 --max-depth 2
```

Вывод — JSON-список смежности. Ключ обозначает пакет с версией, а значение —
его прямые зависимости в пределах анализа:

```json
{
  "A==1.0": ["B==1.5", "C==1.0"],
  "B==1.5": ["D==1.0"],
  "C==1.0": ["E==1.0"],
  "D==1.0": [],
  "E==1.0": []
}
```

Пустой список означает отсутствие найденных исходящих рёбер в пределах
выбранной глубины. Сам по себе он не доказывает отсутствие зависимостей
у граничного пакета.

## Демонстрация третьего этапа

Все примеры используют файлы из `examples/` и не требуют сети:

```bash
bash hw2/examples/run_stage3.sh
```

| Случай | Репозиторий и параметры | Ожидаемый результат |
| --- | --- | --- |
| Ветвление и выбор версии | `branching.json`, `A`, глубина `2` | `A → B==1.5, C`; `B → D`; `C → E` |
| Нулевая глубина | `branching.json`, `A`, глубина `0` | Только `A` |
| Граница глубины | `branching.json`, `A`, глубина `1` | Только связи `A → B, C` |
| Исключение по подстроке | `branching.json`, `A`, фильтр `b` | `A → C → E`; узлов `B` и `D` нет |
| Цикл | `cycle.json`, `A`, глубина `10` | `A → B → C → A`, обход завершается |
| Петля | `cycle.json`, `S`, глубина `10` | `S → S`, обход завершается |
| Общая зависимость | `shared.json`, `A`, глубина `4` | Сохраняются обе связи `A → D` и `C → D`, а также `D → E` |
| Пакет без зависимостей | `branching.json`, `D` | `D` с пустым списком |

Например, цикл можно проверить отдельно:

```bash
bash hw2/run.sh --test-mode --repo hw2/examples/cycle.json \
  --name A --version 1.0 --max-depth 10
```

```json
{
  "A==1.0": ["B==1.0"],
  "B==1.0": ["C==1.0"],
  "C==1.0": ["A==1.0"]
}
```

## Как устроен обход

- `core/arguments_parser.py` создаёт CLI по модели параметров.
- `main/domain/entities/parameters.py` проверяет значения опций.
- `main/data/external_api/dependencies_collector.py` получает сведения
  из JSON Simple API и отдельных файлов `.metadata`.
- `main/data/file_dependencies_collector.py` читает те же сведения из JSON.
- `main/domain/dependencies_repository.py` описывает общий интерфейс источников.
- `main/domain/dependencies_tree_builder.py` обходит очередь по уровням.
  Запросы одного уровня выполняются параллельно с лимитом; следующий уровень
  начинается после завершения текущего. Прямые зависимости кешируются
  на время одного запуска. Ключ учитывает имя, версию и выбранные extras.
- Повторение пакета на текущем пути сохраняется как конечный узел с обратной
  связью. Поэтому цикл не вызывает бесконечного обхода. Общие зависимости
  раскрываются в каждой доступной ветке из кеша.
- `Dependency.as_adjacency_list()` итеративно объединяет узлы и рёбра для
  вывода, включая обратные рёбра и эквивалентные версии `1.0` и `1.0.0`.

Для каждой зависимости выбирается максимальная подходящая версия отдельно.
Разрешения конфликтов ограничений между разными ветками, как в pip, нет.
Сетевой источник пока требует JSON Simple API и отдельные `.metadata`;
HTML-индексы и извлечение метаданных из архивов не поддерживаются.
`packaging` используется для разбора имён, требований и версий; сетевые
запросы и обход графа выполняет код приложения.

## Проверки и ошибки

```bash
.venv/bin/python -B -m unittest discover -s hw2/tests -v
```

Тесты проверяют BFS, глубину, фильтрацию, циклы, общие зависимости,
длинные цепочки без рекурсии, выбор версий, файловый формат и запуск
через `run.sh`. Сетевой источник проверяется с подставными HTTP-ответами.

Отдельные сценарии на Bash состоят из прямых вызовов `run.sh`.
Перед каждой командой выводится пояснение, затем результат приложения.
Журналы `.stdout` и `.stderr` не создаются, весь вывод виден в терминале.

| Скрипт | Что проверяет | Нужна сеть | Нужен D2 |
| --- | --- | --- | --- |
| `tests/test_mode.sh` | JSON-репозиторий, версии, глубина, фильтр, общие зависимости и циклы | Нет | Нет |
| `tests/test_load_order.sh` | Вывод порядка загрузки, фильтр и глубина | Нет | Нет |
| `tests/test_visualization.sh` | Создание SVG с ветвлением, фильтром и циклом | Нет | Да |
| `tests/test_errors.sh` | Коды ошибок параметров, файла, пакета, версии и циклического порядка | Нет | Нет |
| `tests/test_pypi.sh` | Реальный PyPI и SVG для httpx, requests и rich | Да | Да |

Общий запуск, включая реальный PyPI:

```bash
bash hw2/tests/run_all.sh
```

Без сети, с пропуском сценария PyPI:

```bash
bash hw2/tests/run_all.sh --offline
```

Флаг `--offline` сохраняет проверку SVG, поэтому для общего запуска нужен
D2. Установка описана ниже. Отдельный сценарий можно запустить напрямую:

```bash
bash hw2/tests/test_mode.sh
bash hw2/tests/test_pypi.sh
bash hw2/tests/test_visualization.sh
```

Все сценарии вычисляют пути относительно своего расположения и работают
из любого рабочего каталога. Для Python используется `PYTHON`, проектная
`.venv` или `python3`, как при обычном запуске.

Сохраняются картинки и исходные `.d2` внутри `hw2/output/tests/`:

```text
visualization/  branching.svg, filtered.svg, cycle.svg и исходные .d2
pypi/           httpx.svg, requests.svg, rich.svg и исходные .d2
```

В `.sh` автоматически проверяется успешность запуска, коды ожидаемых ошибок
и наличие непустых SVG. Графы и порядки выводятся для просмотра; их точное
содержимое проверяют Python-тесты. Браузер сценарии не открывают.

`set -e` останавливает сценарий при первой неожиданной ошибке команды.
В `test_errors.sh` маленькая функция `expect_error` сравнивает полученный
код завершения с ожидаемым. Общий скрипт тоже останавливается при сбое,
а при успехе всех запусков печатает `OK: все сценарии прошли`.

Неверные опции завершают запуск с кодом `2` и сообщением argparse.
Недоступный файл, неверный JSON, неизвестный пакет, отсутствующая версия
и ошибки репозитория завершают запуск с кодом `1`, без трассировки стека.
Успешный запуск возвращает `0`. Примеры ошибок:

```bash
bash hw2/run.sh --name A --version 1.0 --max-depth -1
bash hw2/run.sh --test-mode --repo hw2/examples/missing.json \
  --name A --version 1.0
bash hw2/run.sh --test-mode --repo hw2/examples/branching.json \
  --name Z --version 1.0
```

## Этап 4: порядок загрузки

`--format order` выводит каждый пакет ровно один раз, зависимости — раньше
использующих их пакетов. Корень находится в конце. Это логический порядок
в пределах исследованного графа: приложение само не устанавливает пакеты.
Глубина и фильтр действуют так же, как при выводе JSON.

```bash
bash hw2/run.sh --test-mode --repo hw2/examples/branching.json \
  --name A --version 1.0 --max-depth 10 --format order
```

```text
D==1.0
B==1.5
E==1.0
C==1.0
A==1.0
```

Алгоритм Кана начинает с вершин без зависимостей. После обработки пакета
он уменьшает число необработанных зависимостей у его родителей. Из готовых
вершин выбирается минимальная подпись по порядку строк Python. Поэтому
порядок повторяемый, хотя между независимыми пакетами допустимы перестановки.
Обход не использует рекурсию.

Если обнаружен цикл, режима строгого порядка для него нет: приложение
завершается с кодом `1` и перечисляет неупорядоченные узлы. Список может
включать как сам цикл, так и пакеты, зависящие от него. Частичный порядок
не выдаётся как успешный результат. Построение графа и визуализация циклов
при этом поддерживаются.

Демонстрации на ветвлении, общей зависимости, одиночном пакете и цикле:

```bash
bash hw2/examples/run_stage4.sh
```

[Документация pip](https://pip.pypa.io/en/stable/cli/pip_install/#installation-order)
обещает установку зависимостей раньше родителей, но не фиксирует порядок
независимых пакетов. Для циклов pip использует собственное правило разрыва,
а этот инструмент сообщает, что строгий порядок невозможен.

## Этап 5: D2 и изображение

Для вывода исходного D2 установка рендерера не нужна:

```bash
bash hw2/run.sh --test-mode --repo hw2/examples/cycle.json \
  --name A --version 1.0 --max-depth 10 --format d2 \
  --output hw2/output/cycle.d2
```

В диаграмме стрелка `A → B` означает «A зависит от B». Корень выделяется
голубым цветом. Один пакет с одной версией имеет одну вершину, общие связи,
петли и обратные рёбра сохраняются. Подписи экранируются, а идентификаторы
`n0`, `n1`, … не зависят от специальных символов в именах.

Для SVG нужен [D2](https://d2lang.com/tour/install/). На Linux x86-64/ARM64
его можно установить локально, без изменения системы:

```bash
.venv/bin/python -B hw2/tools/install_d2.py
```

Скрипт скачивает официальный релиз **0.9.0**, проверяет SHA-256 архива
по данным [GitHub Release](https://github.com/d2lang/d2/releases/tag/v0.9.0)
и извлекает только бинарник в `hw2/.tools/d2`. Каталог исключён из Git.
На других системах используйте установку из документации D2.
Поиск рендерера: переменная `D2_BINARY`, затем `d2` из `PATH`, затем
локальный `hw2/.tools/d2`.

```bash
bash hw2/run.sh --test-mode --repo hw2/examples/cycle.json \
  --name A --version 1.0 --max-depth 10 --format d2 \
  --output hw2/output/cycle.svg --show
```

Рядом с SVG сохраняется исходный `.d2`. Опция `--show` передаёт изображение
стандартному браузеру; без неё файлы только сохраняются. Если браузер нельзя
запустить, SVG можно открыть вручную. Ошибки D2 дают код `1`; старый SVG
заменяется только после успешной компиляции нового. Внешний процесс
запускается без shell, с таймаутом 30 секунд.

Три реальных пакета для демонстрации: `httpx==0.28.1`, `requests==2.32.3`,
`rich==13.9.4`. Команда требует сеть и установленный D2:

```bash
bash hw2/examples/run_stage5.sh
# Открывать каждую диаграмму после создания:
bash hw2/examples/run_stage5.sh --show
```

Файлы сохраняются в `hw2/output/`. Это генерируемые артефакты, каталог
исключён из Git.

## Сравнение с pip и pipdeptree

Для воспроизведения сравнений этапов 4–5:

```bash
.venv/bin/python -B -m hw2.tools.compare_with_pip
```

Скрипт работает отдельно от приложения:

1. Получает граф самостоятельным сборщиком приложения с глубиной 100.
2. Сохраняет JSON, порядок загрузки, D2 и SVG.
3. Создаёт отдельное окружение для каждого пакета и действительно устанавливает
   туда выбранную версию через pip. Сохраняет `pip-report.json` и журнал.
   Фактический порядок берёт из строки `Installing collected packages`,
   а не из `--dry-run`, алфавитного `Would install` или порядка в JSON-отчёте.
4. Получает независимые JSON и SVG через `pipdeptree==2.30.0`.
5. Сравнивает имена и версии узлов, направленные рёбра и допустимость обоих
   порядков. Эквивалентные имена и версии нормализуются.

Для эталонного SVG используется
[pipdeptree с Graphviz](https://github.com/tox-dev/pipdeptree). Это сторонний
инструмент экосистемы pip; отдельной штатной команды визуализации графа
у самого pip нет. На компьютере должен быть установлен `dot` из Graphviz.
Приложение не использует pip или pipdeptree для собственного сбора зависимостей.

Каталоги окружений и инструментов находятся в `hw2/.cache` и `hw2/.tools`,
включены в `.gitignore`. Проектная `.venv` используется как интерпретатор,
её пакеты скрипт не устанавливает и не обновляет. Для сравнения скачиваются
только wheels, исходные архивы не собираются.

Сохранённые примеры находятся в `examples/results/`:

- `graph.json`, `graph.d2`, `graph.svg` — результаты приложения;
- `order.txt` — порядок загрузки приложения;
- `pip-install.log`, `pip-report.json` — фактическая установка pip;
- `pipdeptree.json`, `pipdeptree.svg` — независимый эталон;
- `comparison.json` — различия и проверки порядков;
- [comparisons.md](examples/comparisons.md) — разбор полученных результатов.

Различия расположения узлов и подписей стрелок не означают различий состава
графа. Расхождения версий возможны: собственный сборщик пока не выполняет
глобальное разрешение конфликтов и не отбирает дистрибутивы по совместимости
Python и платформы так, как это делает pip. Для корректного сравнения без
обрезания ветвей используйте одинаковые условия и достаточную глубину.

Этапы реализованы функционально. Для фиксации в истории предусмотрены
отдельные коммиты; в рамках изменений только внутри `hw2/` они не создаются.
